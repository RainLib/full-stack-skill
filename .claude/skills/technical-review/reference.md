# 技术评审参考指南

## 评审维度清单

### 架构可行性

- [ ] 技术选型能否满足所有 P0 功能需求？
- [ ] 非功能需求（性能、安全、兼容性）能否达标？
- [ ] 技术栈内各组件版本是否兼容？
- [ ] 是否存在过度工程（用了不必要的复杂方案）？

### API 契约

- [ ] 所有核心功能是否都有对应的 API 接口？
- [ ] 接口命名是否遵循 RESTful 规范（或 GraphQL schema 是否合理）？
- [ ] 请求/响应 schema 是否包含所有必要字段？
- [ ] 错误码是否统一、可枚举？
- [ ] 分页、排序、过滤的约定是否明确？
- [ ] 认证/授权在 API 层是否体现？

### 数据模型

- [ ] 核心实体是否覆盖了需求中的所有数据概览？
- [ ] 字段类型和约束是否合理（长度、精度、NOT NULL）？
- [ ] 实体关系（1:1、1:N、N:N）是否正确？
- [ ] 是否需要索引？高频查询字段是否有索引建议？
- [ ] 软删除 vs 硬删除策略是否明确？

### 安全

- [ ] 认证方案是否覆盖所有需要保护的接口？
- [ ] 敏感数据（密码、Token）是否加密存储？
- [ ] 输入校验是否在 API 层实施？
- [ ] SQL 注入、XSS 等常见攻击是否有防护？
- [ ] CORS 策略是否合理？

## API 设计规范参考

### RESTful 路径约定

```
GET    /api/{resources}          → 列表（支持分页/筛选）
POST   /api/{resources}          → 创建
GET    /api/{resources}/{id}     → 详情
PUT    /api/{resources}/{id}     → 全量更新
PATCH  /api/{resources}/{id}     → 部分更新
DELETE /api/{resources}/{id}     → 删除
```

### 统一响应格式

```json
{
  "code": 0,
  "message": "success",
  "data": {}
}
```

### 分页约定

```
GET /api/orders?page=1&size=20&sort=createdAt,desc
```

```json
{
  "data": {
    "items": [],
    "total": 100,
    "page": 1,
    "size": 20,
    "pages": 5
  }
}
```

### 统一错误格式

```json
{
  "code": 40001,
  "message": "参数校验失败",
  "details": [
    { "field": "email", "message": "格式不正确" }
  ]
}
```

## 常见风险类型

| 类型 | 示例 | 常见对策 |
|------|------|----------|
| 技术风险 | 新框架/库团队不熟悉 | 预留学习时间、准备 fallback |
| 性能风险 | 大数据量查询慢 | 分页、索引、缓存 |
| 安全风险 | JWT 泄露 | 短过期时间 + refresh token |
| 依赖风险 | 第三方 API 不稳定 | 降级方案、重试、熔断 |
| 集成风险 | 前后端接口不匹配 | API 契约先行、联调计划 |
| 数据风险 | 数据迁移出错 | 迁移脚本 + 回滚方案 |

## 评审结论标准

| 结论 | 条件 | 后续动作 |
|------|------|----------|
| **通过** | 无阻塞问题，风险可控 | 直接进入程序设计 |
| **有条件通过** | 有 1~3 个必须修正项，但不影响整体架构 | 修正后进入程序设计 |
| **不通过** | 架构方案有根本性问题 | 需要重做技术选型 |
